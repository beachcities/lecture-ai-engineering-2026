- 第1回（素のLLM）とエージェントの回答の違い：第1回の `app.ask`（gemini-3.5-flash-lite）は、「AIE2026の講座の宿題にある「3レベル」とは何ですか？」に対して講座名を推測し、一般的な3段階（ビギナー／スタンダード／チャレンジ）を答えた。第3回の `app.agent` は同じモデル・同じ質問で、用語集の homework-levels の定義どおり「基礎（講義内容の確認）」「実装（自分でコードを書く）」「発展（調査や試行）」の3段階、どれか1つで完了、原則として採点しないと答え、最後に「関係する回：第1回」を付けた（用語集の lecture: 1 と一致）。
- `--trace` で見えたツール呼び出し（ツール名と引数）：「LoRA とQLoRAの違いは？」で `search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回。docstring の「query には調べたい用語を1つだけ入れる」のとおり、用語ごとに分けて検索した。
- 1つの質問での LLM 呼び出し回数（`requests`）：上の質問で requests=2、tool_calls=2（入力 1196 / 出力 181 トークン）。ツール呼び出しは2回だが LLM の呼び出しは2回で、1回目の応答で2つの検索をまとめて依頼し、2回目で結果を受けて回答したと読める。
- 追加したツールと、docstring に書いた説明：`make_quiz(lecture: int) -> str`。docstring は「指定した回（1始まりの整数）の用語から1つを選び、確認問題と答えを返す。「第2回の確認問題を出して」のように、復習用の問題を求められたときに使う。lecture には回の番号を入れる（例: 2）。」。用語集から lecture が一致する用語を集めて random.choice で1つ選び、{"question": "「○○」の意味は？", "answer": definition} を JSON で返す。用語が無い回（pytest のダミー引数 lecture=0 など）では、落ちずに用語がある回の一覧を返す。`--list-tools` で3つ目のツールとして見え、「第2回の内容から確認問題を1問出して」で `make_quiz({'lecture': 2})` が呼ばれた（requests=2、tool_calls=1）。`uv run pytest -q` は 11 passed。
- 気づいたこと：make_quiz は答え（「量子化」の definition）も返したが、エージェントは問題だけを出し、答えは書かずに「考えてみた後で答え合わせを」と促した。INSTRUCTIONS の「宿題の答えそのものは書かず、考え方のヒントで導く」が効いたと推測している（確かめてはいない）。また、この質問では search_glossary も get_lecture_summary も呼ばれなかった。

## 宿題

- 取り組んだレベル：実装
- やったこと：
  - `app/tools.py` に `save_learning_log(title: str, content: str) -> str` を追加した。`learning_log/` が無ければ作り、「日時_見出し.md」の名前で Markdown を書く（見出しのファイル名に使えない文字と空白は `_` に置き換え、日時を入れて上書きを避ける）。docstring には「学習の記録を残すよう頼んだときだけ使う」「保存の前に利用者の確認が入る」と書いた。
  - `app/agent.py` で `agent.tool_plain(tools.save_learning_log, requires_approval=True)` と登録し、`output_type=[str, DeferredToolRequests]` を加えた。
  - CLI に `ask_approvals()` を追加した。承認待ちの呼び出しごとにツール名と引数を表示して `[y/N]` を聞き、y なら `True`、それ以外は `ToolDenied("利用者が保存を許可しませんでした。")` を `DeferredToolResults.approvals` に入れる。既定（空 Enter など）は拒否。`main()` では、出力が `DeferredToolRequests` の間、`message_history=result.all_messages()` と `deferred_tool_results=` を渡して `run_sync` をやり直す。続きでまた承認待ちになっても回るよう `while` にした。
  - 再開した実行の `[usage]` が2回目の分しか数えなかったので、`usage=result.usage` を渡して1回目と合計するようにした。
  - 承認の入力を `unicodedata.normalize("NFKC", ...)` で半角にそろえた（下の「結果」の拒否の回を受けて直した）。
- 結果：同じ質問「LoRAについて今日学んだことを、学習の記録として保存して」を2回実行した（gemini-3.5-flash-lite、`--trace` 付き）。
  - 1回目（拒否）：`search_glossary({'query': 'LoRA'})` の後に `save_learning_log({'title': 'LoRAの学習記録', 'content': ...})` が呼ばれ、実行の前で止まって確認を求められた。日本語入力のまま全角の「ｙ」を打ったため、拒否として扱われた。ファイルは書かれず、`[tool return] save_learning_log -> 利用者が保存を許可しませんでした。` がモデルに返り、モデルは「利用者の確認が取れなかったため保存を中止しました」と答えて、用語集の定義を本文に載せた。
  - 2回目（承認、NFKC の修正後）：同じ順で2つのツールが呼ばれ、全角の「ｙ」で承認された。`learning_log/20261106-001654_LoRAの学習記録.md` に保存され、モデルは保存先を示して答えた。`[usage]` は requests=3、tool_calls=2（入力 2549 / 出力 292 トークン）。LLM を呼んだのは、調べる・保存を依頼する・保存結果を受けて答える、の3回と読める。
  - `uv run pytest -q` は 11 passed（`test_agent` は承認待ちの呼び出しを「戻り値が無いもの」として数える）。
- 気づき・疑問：
  - 承認待ちで止まる場所はツールの実行の直前で、モデルは保存したい内容（title と content）を引数として先に全部書いている。利用者は「何を保存しようとしているか」を見てから判断できる。講義の in（毎回承認）に当たる形だが、content が長いと読まずに y を押しそうで、「承認が形だけになりやすい」という講義の指摘を手元で感じた。
  - 全角の「ｙ」が拒否になったのは、既定を拒否にしていたので安全側に倒れた。ただ、利用者が「はい」のつもりで打った入力を拒否するのは使いにくいので、入力を正規化した。確認を挟む設計では、判定ロジックの側の入力の揺れも失敗の原因になると分かった。
  - 拒否したとき、モデルは保存を中止したと正直に伝え、別の手段（本文に載せる）に切り替えた。拒否の理由（ToolDenied の文）がそのままモデルに渡るので、理由の書き方でその後のふるまいが変わりそう（試してはいない）。
  - 保存ファイル名の日時は 00:16 で、日本時間（09:16）ではなかった。Codespaces の時刻が UTC になっているためと思われる（確かめてはいない）。
  - 承認待ちの間は会話の状態（message_history）をプログラム側で持っていて、プロセスが落ちると続きから再開できない。講義の冪等性の話（保存した時点から再開すると二重に実行される）と合わせると、Web 版にして承認を後から受け取るなら、承認待ちの状態の保存と、同じ保存を二度しない工夫が要りそう。
